# M6 independent gateway checks

M6 supplies one MCP doorway. External users authenticate with personal gateway keys; the gateway discovers upstream tools and records each execution attempt before dispatch. These checks use three controlled MCP peers and in-memory identity/registry/audit stand-ins. They prove M6 behavior independently, not real PostgreSQL integration or real shop changes.

## Files to understand

| File | Purpose |
|---|---|
| `backend/gateway/server.py` | Stateless MCP endpoint and authenticated tools preview. |
| `backend/gateway/discovery.py` | Complete bounded discovery, stable public names, cache/status/version checks. |
| `backend/gateway/router.py` | Shared tool executor and one-attempt audit/cancellation lifecycle. |
| `backend/gateway/upstream_client.py` | Short-lived MCP sessions, checked numeric DNS dialing, original TLS hostname and byte limits. |
| `backend/gateway/schema.py` | Explicit schema subset that rejects unsafe patterns/references before validation. |
| `backend/gateway/context.py` | Trusted UUID correlation and safe per-invocation activity metadata for M7. |
| `scripts/m6/harness.py`, `standins.py`, `fixtures.py` | Disposable isolated application and controlled peers. |
| `scripts/m6/prepare.py`, `check-m6.py` | Owned namespace/Secret preparation and live checks with sanitized evidence. |

The full detailed design is [M6 section 10](../../modules/m6-spec.md). Original names up to 200 characters are supported; unsafe/long public names become stable hash aliases. Schemas have explicit size/depth/node/composition bounds. Network/local references and unreviewed regex patterns are rejected clearly, rather than evaluated unboundedly. The five accepted patterns include the existing local tool patterns and are provider independent. Compressed upstream replies are explicitly unsupported; rich content cannot be silently dropped or presented as complete after truncation.

## Reproduce in PowerShell

Run from the repository root. Docker Desktop and the existing `k3d-urumi` cluster must already be available. Use the approved locked dependencies in a project-local M6 environment. Credentials generated by preparation stay in ignored `.tools/m6/access.json` and a dedicated Kubernetes Secret; never print or commit them.

```powershell
& .tools/m6/venv/Scripts/python.exe -m pytest tests/gateway -q --assert=plain -p no:cacheprovider --basetemp .tools/m6/pytest-check
& .tools/m6/venv/Scripts/python.exe -m scripts.m6.prepare
docker build --target checks -t urumi/gateway-check:m6 -f backend/Dockerfile .
docker run --rm urumi/gateway-check:m6 python -m pip check
& .tools/m1/k3d.exe image import urumi/gateway-check:m6 -c urumi
& .tools/m1/helm.exe upgrade --install urumi-m6-check deploy/charts/urumi --kubeconfig .tools/m1/kubeconfig.yaml --kube-context k3d-urumi -n urumi-m6-check -f tests/gateway/values-check.yaml --wait --timeout 180s
& .tools/m6/venv/Scripts/python.exe -m scripts.m6.verify_cluster
& .tools/m6/venv/Scripts/python.exe scripts/m6/check-m6.py --cleanup
```

`verify_cluster` first checks the four deployed runtime image IDs against the Docker-exported configuration digest and performs the actual allowed-denied-allowed NetworkPolicy check, saving only safe evidence. It is a host helper added for reproducibility; it is not part of the frozen runtime image.

The runner owns a hidden loopback port-forward on `127.0.0.1:18008` and closes it in `finally`. It checks the namespace ownership label before mutation, saves original `urumi` Pod/PVC identities, scales only its controlled header fixture to zero, confirms other peers still work, then restores it. The header fixture uses stateful Streamable HTTP with SSE; the other two use stateless JSON responses. This tests both upstream response forms while the external gateway remains stateless.

The test-only `/test/state` route accepts the generated admin fixture key and exposes safe fixture controls/audit summaries. It is part of the isolated harness only, not a production management API. No test controls are wired into the final backend by this module. Fixture secrets are artificial/random, but still withheld from logs and artifacts.

The runner deletes `urumi-m6-check` only after successful runtime checks when `--cleanup` is supplied. On failure it preserves the owned fixture namespace and partial results for investigation. Do not delete or recreate the original `urumi` namespace or its persistent disks. Reset a failed acceptance run by redeploying only the owned disposable harness after investigating the saved check/failure type; do not automatically replay uncertain tool calls.

## Evidence and interpretation

The 52 distinct host cases are recorded across `host-tests.txt` (41), `host-catalog-tests.txt` (six), `host-isolation-identity-tests.txt` (three) and `host-upstream-auth-tests.txt` (two actual wrong bearer/header cases). The subsequent preview-envelope assertion reuses an existing method, so it does not add a distinct test. Temporary TLS certificate creation required running pytest outside the filesystem sandbox; certificate material remains in ignored temporary directories.

Saved live evidence is `cluster-results.json`, `cluster-audit-status.json`, `cluster-resources.json` and `gateway-log.txt`. Runtime status `PASS_RUNTIME_REVIEW_PENDING` records checks before independent review; the separate `acceptance-results.json` and `acceptance-review.md` now record all 12 criteria PASS with user acceptance pending, preserving the original measured results. Full raw upstream payloads and credentials are not evidence artifacts. OCI image index and runtime configuration digest are different identifiers; use `scripts/m4/image_identity.py` to verify actual image configuration bytes if checking Pod image identity.

Audit fixture rows include UUID identities, UTC start/finish, duration, names and honest outcomes. Timeout or cancellation after submission cannot prove a remote write was undone. A failed finalization leaves `running`; M5's already independently checked exclusive-owner recovery handles real persisted prior-run rows during later integration. Do not treat this in-memory harness as persistence/restart proof.

M10 still owns actual M5/gateway/chat wiring, real WooCommerce/Inventory/Microsoft Learn aggregation, Codex/Inspector compatibility, browser behavior and the two-user definition of done.
